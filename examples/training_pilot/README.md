# What the first training runs actually taught us

The public source includes the summaries and original content identities below. Raw run-object stores and model adapters remain local. Archive verification commands require restoring those stores first; the source-only test run reports their absence explicitly.

The first A100 run proved that a small LoRA SFT step could execute. Its result and code identity are in [the SFT evidence card](sol_sft_smoke_evidence.json). It was a plumbing check with two valid examples, not a comparison between vulnerable and sealed reward.

The next experiment connected a trusted GRPO trainer on Sol to a Mac-side Docker reward worker. The model generated candidate source as JSON data on Sol. Only the Mac worker wrote candidate files and ran the verifier. Both arms used the same Qwen2.5-Coder 3B snapshot, seeds 11, 22, and 33, two update steps, two generations per batch, and the same task prompt. The intended difference was the training reward: a proxy that included candidate-controlled Pytest configuration versus a sealed channel that projected only `solution.py` into the verifier. A separate audit was not used as training reward.

The [first archived paired run](grpo_bridge_d/index.json) completed six conditions on one class A100, but the model returned JSON inside Markdown code fences. The bridge had required bare JSON, so all 24 samples were marked `INVALID_OUTPUT` and received zero reward. Every within-batch reward standard deviation was zero. Each vulnerable and sealed adapter was byte-identical for its seed. This is a useful failure of the experiment design, not evidence that either evaluator improved the model.

The parser was then changed to accept one exact fenced JSON object and an empty optional `conftest.py`. The [second archived paired run](grpo_bridge_e/index.json) again completed six conditions. All 24 `is_even` solutions passed, so every reward was one. Reward standard deviation and training loss remained zero, and the paired adapters were again byte-identical by seed. The wire-format failure was fixed, but the task was too easy to supply a learning signal.

The [third archived run](grpo_bridge_f/index.json) used a harder SemVer task. Its fixed control matrix had two legitimate positives, two ordinary negatives, and a seeded proxy-pass/audit-reject exploit. The live 3B model did not receive positive training reward. Of 24 sampled completions, 18 were malformed or cut off by the 256-token limit and six were valid but semantically rejected. Both arms again received only zero reward, and their adapters remained byte-identical by seed. This is a model-output and task-design result, not a demonstrated repair benefit. The third archive also binds each evaluated result to task, candidate, verifier, policy, provider, and workspace identities.

The [first tagged-output preflight](grpo_bridge_g/index.json) tested one vulnerable-reward seed with a 1,024-token completion budget. It failed before an optimizer update. The trainer system message still asked for JSON while the task asked for file blocks, and generated `solution.py` content started with a Markdown fence. Pytest collection could not import that candidate. The reward worker stopped training because it classified the candidate syntax error as `VERIFIER_FAILURE`. That classification was a bug, not evidence that the verifier itself failed. Its failed report and the two evaluated outputs remain in the single-condition archive. This is not a paired comparison.

We corrected the conflicting system message and added a syntax check that treats malformed candidate Python as `INVALID_OUTPUT`, while genuine verifier failures still stop the run. The [second tagged-output preflight](grpo_bridge_h/index.json) completed two GRPO steps on one A100. Its four samples produced three invalid outputs and one syntactically valid but incorrect solution, so the rewards were all zero. The recorded gradient norm and loss were both zero at both steps. It did not produce a learned advantage or justify expanding to three seeds. Its adapter is retained only in ignored local storage; the retained local archive records its digest.

The [third preflight](grpo_bridge_i/index.json) used a separately frozen diagnostic reward: a proxy pass earns 1, malformed output earns 0, and a runnable rejected solution earns the fraction of seven visible tests it passed. The same reviewed verifier supplied the counts. In seed 11, the first sampled batch earned 0 and 1/7, so its reward standard deviation and gradient norm were nonzero. The first step reported gradient norm `0.06798729300498962`; the second batch again had only zero rewards. The completed adapter digest differs from H's zero-gradient adapter digest. This proves that the trainer can update on real Mac Docker feedback, not that it learned a better coding policy.

We then ran the [matching sealed arm](grpo_bridge_i_paired/index.json) with the same frozen configuration and seed. Both arms generated byte-identical completions, received the same reward sequence, logged the same loss and gradient norms, and produced byte-identical adapters. No sampled completion supplied a candidate-controlled `conftest.py` exploit, so the two evaluators had nothing to disagree about. This one-seed pair is an informative negative control, not evidence that sealing does or does not help when actual reward hacking occurs. It has no held-out audit or downstream performance measurement.

This is why a completed GPU job is not the release study. A valid comparison needs a larger frozen task corpus, an agent opportunity to encounter evaluator weaknesses, reviewed SFT data, the same reward rule across both arms, and a hidden audit for both trained arms. Preflight I established one step of reward contrast in each arm, but no difference between arms.

A later [scripted three-candidate preflight](controlled_population_v1/README.md) used the same `is_even` positive, an ordinary-invalid solution, and that same wrong solution paired with a disclosed candidate-controlled `conftest.py`. With identical candidate bytes and the existing Mac Docker reward worker, the vulnerable arm returned `[1, 0, 1]` and the sealed arm returned `[1, 0, 0]`. A separate post-reward audit returned `PASS`, `REJECT`, `REJECT`. The retained local archive includes 48 verified content-addressed objects, including driver source, candidate bytes, verifier source, reward exchanges, bound evaluator results, and audit results. This establishes a causal reward-path difference for a hand-selected fixture. No model generated these candidates, no optimizer step used this population, and no downstream gain is claimed. The next ML gate is to elicit or otherwise freeze a model-produced population with actual reward contrast, then run the charter's multi-seed study with held-out audits.

The paired archives contain content-addressed configuration, trusted driver source, model completions, reward requests and responses, evaluated candidate files, raw process evidence, and training reports. D, E, and F have six reports each; the diagnostic I pair has two. F and I also include frozen verifier source and bound-result receipts. The single-condition archives preserve G, H, and the first I arm separately. Adapter digests and sizes are recorded where available, but adapter binaries remain in ignored local storage rather than Git. The first paired archive lacks one earlier frozen worker-source byte object after its parser changed; its configuration still records that source hash, and the limitation is not hidden.

Verify the original evidence after restoring an authorized local archive:

```bash
python -m pytest -q tests/unit/test_reward_pilot_archive.py
python -m pytest -q tests/unit/test_reward_pilot_analysis.py
python -m pytest -q tests/unit/test_reward_preflight_archive.py
python -m pytest -q tests/unit/test_reward_population_archive.py
```

To analyze a privately retained Sol adapter copy as well, run `python scripts/analyze_reward_pilot.py --help`. The analyzer checks the six reports against the same reward receipts and recomputes adapter SHA-256 identities. It returns `downstream_improvement_established: false` even when every training process completed.
